## 2. ปัญหาด้านการเก็บข้อมูล

### 2.1 Google ส่งหน้าเว็บคนละแบบในแต่ละครั้งที่โหลด

**อาการ** รีวิวหยุดอยู่ที่ 5 ใบ แล้วไม่เพิ่มอีกเลย ทั้งที่ร้านมีรีวิวหลายร้อย

**สาเหตุจริง** Google ส่งหน้าได้ 3 แบบสำหรับ URL เดียวกัน
- แบบ A ไม่มีแท็บรีวิวเลย
- แบบ B มีรีวิว 5–10 ใบ แล้วมีปุ่ม "ดูรีวิวเพิ่มเติม" ที่กดแล้วเจอกำแพงให้ล็อกอิน
- แบบ C ฟีดปกติ เลื่อนแล้วโหลดเพิ่มทีละ 10

**ทางที่ลองแล้วไม่ได้ผล** เปลี่ยน IP (ผู้ใช้ลองหลายรอบ ได้ค่าเท่าเดิม)

**วิธีแก้** `detect_limited_view()` ตรวจว่าเจอหน้าแบบจำกัดไหม ถ้าใช่ให้โหลดซ้ำ
สูงสุด 3 ครั้งแล้วเก็บผลที่มากที่สุด และ **ไม่ตัดโควตา `deep_attempts`**
เมื่อเจอหน้าแบบจำกัด เพราะไม่ใช่ความผิดของร้านนั้น

**ที่ผมสรุปผิดระหว่างทาง** ตอนแรกบอกว่าโหลดซ้ำแล้วจะพลิกเป็นแบบ C ได้ —
สรุปจากตัวอย่าง 2 ครั้ง พอทดสอบจริง 30 ครั้งติดกันได้แบบ A ทั้งหมด
ข้อสรุปที่ถูกคือ "ขึ้นกับช่วงเวลาและปริมาณการเรียก" ไม่ใช่ "โหลดซ้ำแล้วได้"

### 2.2 ค้นด้วยชื่อร้านแล้วได้รีวิวของสาขาอื่น

**อาการ** ร้านในพิษณุโลกมีรีวิวที่พูดถึงสาขากรุงเทพปนมา

**สาเหตุ** ใช้ `search_query` เป็นชื่อร้าน Google จึงเลือกสาขาให้เอง

**วิธีแก้** เปลี่ยนไปใช้ `https://www.google.com/maps/place/?q=place_id:<id>`
ซึ่งชี้ไปที่ร้านนั้นตรง ๆ ไม่ผ่านการค้นหา

### 2.3 พื้นข้อความ 40 อักขระตัดรีวิวจริงทิ้ง

**อาการ** หน้าหนึ่งเก็บได้ 97 รีวิว ทั้งที่เห็นในหน้าเว็บมากกว่านั้น

**สาเหตุ** ตัวกรองเดิมทิ้งรีวิวที่สั้นกว่า 40 อักขระ แต่รีวิวไทยจำนวนมากสั้นกว่านั้น
และยังเป็นรีวิวจริง เช่น "อร่อย บริการดี"

**วิธีแก้** ลดเหลือ 5 อักขระ (`MIN_REVIEW_TEXT_LEN`) — หน้าเดียวกันได้ 166 รีวิว
และจากการเก็บรอบนั้น 278 จาก 757 รีวิวใหม่เป็นรีวิวสั้น

### 2.4 คีย์กันซ้ำใช้แค่ 60 อักขระแรก

รีวิวที่ขึ้นต้นเหมือนกันแต่เนื้อหาต่างกันถูกมองว่าซ้ำและทิ้งไป
แก้โดยใช้ข้อความเต็มเป็นคีย์

## 3. ปัญหาด้านคุณภาพข้อมูล

### 3.1 รีวิวที่ "ให้ดาวอย่างเดียว" ปนอยู่ในตัวส่วนของทุกสัดส่วน

**อาการ** ผู้ใช้สังเกตว่ารีวิวบางอันใน "กลางๆ" มีแต่ชื่อคน

**สาเหตุ** ผู้รีวิวที่กดดาวแล้วไม่เขียนอะไร ยังมีการ์ดที่ประกอบด้วยชื่อผู้รีวิว
ไอคอนดาว วันที่ และเมตา เช่น `฿200-300` — `clean_review_text()` ตัดไอคอนกับคำ UI ได้
แต่ตัดชื่อคนและค่าเมตาไม่ออก เศษที่เหลือจึงถูกเก็บเป็น "เนื้อรีวิว"

**ขนาดปัญหา** 6,021 แถว = 7.62% ของรีวิวที่ระบบถือว่า "มีข้อความ"
และพองหมวด "ความคิดเห็นทั่วไป" ขึ้น 3,944 แถว

**วิธีแก้** เขียน `is_rating_only()` เป็นฟังก์ชัน**ใหม่** โดยอาศัยหลักว่า
"เนื้อรีวิวจริงอยู่บรรทัดถัดจากวันที่เสมอ" ถ้าหลังวันที่มีแต่ไอคอน/เมตา/คำ UI/
คำตอบจากเจ้าของร้าน แปลว่าผู้รีวิวไม่ได้เขียนอะไร
แล้วตั้ง `text_clean = ''` (ไม่ลบแถว เพราะรีวิวนั้นมีอยู่จริงและนับใน `google_reviews_total`)

### 3.2 กับดักที่อันตรายที่สุดของโปรเจกต์ — `text_hash`

`text_hash = md5(clean_review_text(text))` คำนวณตอน INSERT

**ถ้าแก้ `clean_review_text()` แม้แต่นิดเดียว hash ของทุกรีวิวจะเปลี่ยน
แล้วรีวิวเดิมทั้งฐานจะถูก INSERT ซ้ำ** — เคยเกิดแล้วและได้แถวซ้ำ 3,453 แถว

จึงต้องแยก `is_rating_only()` ออกเป็นฟังก์ชันใหม่ ห้ามรวมเข้าไป และเขียนคำเตือน
กำกับไว้ในโค้ดทุกจุดที่เกี่ยวข้อง

**ผลข้างเคียงที่ยังแก้ไม่ได้** `text_clean` 395 แถว (0.54%) ยังขึ้นต้นด้วยวันที่
สัมพัทธ์ เช่น "5 วันที่ผ่านมา อาหารอร่อย..." ซึ่งเป็นเศษจากตัวล้างเดิม
แก้ไม่ได้ด้วยเหตุผลข้างบน ต้องระบุเป็นข้อจำกัดในเล่ม

### 3.3 ป้ายชุดเทรนชุดแรกถูกเขียนทับจนเหลือสำเนาเดียว

โมเดลชุดแรกเทรนด้วยป้ายที่ Claude ติดไว้ 10,690 รายการ (knowledge distillation)
ต่อมา `wangchanberta-finetuned` เขียนทับ `analyzed_reviews` ไป 93,757 แถว
**ป้ายชุดเดิมจึงไม่เหลือในฐานข้อมูลแล้ว** สำเนาเดียวที่เหลือคือ
`data/training/category_dataset.json`

ตรวจพบตอนประเมินว่าจะย้ายไป multi-label — ถ้าไฟล์นั้นหายไปด้วยจะไม่มีหลักฐานเลย
ว่าโมเดลถูกเทรนด้วยอะไร ปัจจุบันสำรองไว้ใน `backup/pre_multiaspect_20261011/`

### 3.4 ข้อมูลรั่วระหว่างชุดเทรนกับชุดประเมิน

ชุด gold 300 รีวิวถูกสุ่มมาจาก `analyzed_reviews` ทั้งหมดโดย**ไม่ได้กันชุดเทรนออก**
ตรวจแล้วพบ **49 รายการ** ที่ข้อความซ้ำกับ split `train`/`val` ของโมเดลหมวดรุ่นเดิม
ถ้ารายงาน F1 บนทั้ง 300 ตัวเลขจะสูงเกินจริง จึงตัดเหลือ **251** รายการ

นอกจากนี้ชุดเทรนเดิมเองก็มี `test` ที่โผล่ใน `train` ด้วย **1.8%** (หมวด)
และ 0.2% (อารมณ์) ทำให้ค่า accuracy 0.6981 ที่เคยรายงานเฟ้อขึ้นเล็กน้อย

**ที่ผมคำนวณผิดระหว่างทาง** ตอนแรกบอกว่ารั่ว 54 รายการ — มาจากการบวก 42+12
ซึ่งนับซ้ำรีวิวที่อยู่หลาย split พร้อมกัน ค่าที่ถูกคือ 49

## 4. ปัญหาด้านการนับและการแสดงผล

### 4.1 กฎข้อ 1 — ตัวเศษกับตัวส่วนต้องผ่านตัวกรองชุดเดียวกัน

เป็นกฎที่ตั้งขึ้นหลังพบว่าหลายจุดบนแดชบอร์ดละเมิดมัน พบและแก้ 4 จุด

| endpoint | ปัญหา |
|---|---|
| `/zones` | คิวรีแรกขาด `biz_filter` · severity นับจากชุดที่ไม่ได้กรองข้อความ |
| `/top-places` | `review_count` ไม่กรอง `text_clean <> ''` แต่ตัวเศษกรอง |
| `/summary` | `total_places`/`total_reviews` ไม่เคารพ `biz_filter` |
| `/positive-highlights` | ตัวส่วนคำนวณจากคิวรีคนละชุดกับตัวเศษ |

ทางแก้เชิงโครงสร้างคือยุบตัวกรองทั้งหมดไว้ที่ `api/filters.py` ไฟล์เดียว
แล้วห้าม copy-paste ไปที่อื่น

### 4.2 ลิสต์หมวดในหน้าเว็บไม่ตรงกับโมเดล

หน้าเว็บพิมพ์ลิสต์หมวดไว้เอง 10 หมวด ขณะที่โมเดลมี 12 หมวด
มีหมวด "พ่อค้าแม่ค้าและการรบกวน" ที่ไม่มีข้อมูลสักแถว และ**ขาดสองหมวดใหญ่ที่สุด**
คือ "รสชาติและคุณภาพอาหาร" (27,025 แถว) กับ "บรรยากาศและการตกแต่งร้าน" (6,958 แถว)
ผู้ใช้จึงกรองสองหมวดนั้นไม่ได้เลย

แก้โดยย้ายรายชื่อหมวดไปไว้ที่ `shared/category_labels.json` ไฟล์เดียว
ให้ทั้ง `api/filters.py` และ `frontend/src/utils/categoryLabel.ts` อ่านจากที่นั่น

### 4.3 แถว "รวมคำบ่นทั้งหมด" ที่ไม่ใช่ทั้งหมด

ตารางแนวโน้มมีแถวชื่อ "รวมคำบ่นทั้งหมด" แต่คิดจาก 5 หมวดที่โชว์เท่านั้น
แก้เป็นสองแถวแยกกัน: "รวม 5 หมวดนี้" กับ "คำบ่นทั้งหมด"

### 4.4 นิยามป้ายไม่เคยถูกเขียนไว้ที่ไหนเลย

พรอมป์ที่ใช้ติดป้ายบอกแค่ว่าตอบได้ 3 ค่า แต่**ไม่มีนิยามว่าแต่ละค่าหมายถึงอะไร**
การตีความจึงเลื่อนได้ตามรอบที่รัน และเวลาเอาคนมาประเมินเทียบ ถ้ากติกาคนละชุด
ค่า kappa จะต่ำเพราะ "กติกาไม่ตรงกัน" ไม่ใช่เพราะโมเดลแย่

แก้โดยสร้าง `shared/sentiment_labels.json` เป็นแหล่งเดียว แล้วให้พรอมป์
คู่มือผู้ตรวจ และเล่ม อ้างจากไฟล์เดียวกัน

## 5. ปัญหาเชิงเทคนิคที่กินเวลาโดยไม่คาดคิด

| ปัญหา | อาการ | สาเหตุ |
|---|---|---|
| asyncpg เดาชนิดพารามิเตอร์ผิด | `:ratio * LEAST(int,int)` ทำให้ 0.5 กลายเป็น 0 เงียบ ๆ | ต้อง `CAST(:ratio AS double precision)` |
| SQLAlchemy `Row` ชนชื่อ | ตั้ง alias เป็น `t` หรือ `s` แล้ว `r.t` คืนทั้งแถวแทนคอลัมน์ | ทำให้ไฟล์ CSV เสียทั้งไฟล์ |
| Postgres ลดรูป alias | `AS L` กลายเป็น `l` | คิวรีที่อ้าง `L` พัง |
| `review_date` ไม่ใช่วันที่ | เก็บข้อความ "6 ปีที่แล้ว" | วันที่จริงอยู่ที่ `review_date_approx` |
| `Decimal` แปลงเป็น JSON ไม่ได้ | รายงานพัง | `json.dumps(..., default=float)` |
| event loop ชนกัน | `TestClient` + async engine ล่ม | ใช้ `httpx.AsyncClient` ใน loop เดียว |
| Git Bash กลืน backslash | heredoc ทำให้ `\n` กลายเป็นขึ้นบรรทัดจริง | เขียนไฟล์ด้วยเครื่องมือเขียนไฟล์แทน |
| dev server ไม่ reload | เพิ่มฟิลด์ใน API แล้วหน้าเว็บไม่เห็น | ต้องรีสตาร์ท uvicorn |

## 6. ส่วนที่ยากที่สุด

### อันดับ 1 — การตัดสินว่า "ตัวเลขที่ได้เชื่อได้แค่ไหน"

ยากกว่าการเขียนโค้ดทั้งหมดรวมกัน เพราะทุกตัวเลขมีทางที่จะสวยเกินจริงโดยไม่รู้ตัว

ตัวอย่างที่เจอจริงในโปรเจกต์นี้
- accuracy 0.9203 ดูดีมาก แต่ทายว่า "บวก" ทุกรีวิวก็ได้ 0.8805 แล้ว
- ชุดประเมินมีข้อความซ้ำกับชุดเทรน 49 รายการ
- threshold ที่จูนบนชุดหนึ่งทำให้ผลบนอีกชุด **แย่ลง** เพราะคนละการกระจาย
- การจำลองด้วย regex บอกว่าอันดับหมวดจะเปลี่ยน แต่พอดูให้ละเอียดพบว่าเป็น
  สิ่งแปลกปลอมของวิธีวัด (คำว่า "บรรยากาศ" โผล่ในคำชมบ่อย จึงถูกนับเป็นปัญหา)
- ป้ายทั้งชุดเทรนและชุดประเมินมาจาก AI ตัวเดียวกัน ความสอดคล้องสูงจึงอาจหมายถึง
  "ผิดเหมือนกัน" ไม่ใช่ "ถูกทั้งคู่"

สิ่งที่ช่วยได้จริงคือการบังคับตัวเองให้**วัดก่อนเชื่อ**ทุกครั้ง และรายงาน baseline
คู่กับผลเสมอ

### อันดับ 2 — การยอมรับว่าสมมติฐานของตัวเองผิด

ในโปรเจกต์นี้มีหลายครั้งที่ข้อสรุปแรกผิดและต้องแก้

| เคยสรุปว่า | ความจริง |
|---|---|
| หน้าแบบจำกัดเป็นถาวร | เป็นชั่วคราว ขึ้นกับช่วงเวลา |
| โหลดซ้ำแล้วจะได้ฟีดเต็ม | ทดสอบ 30 ครั้งได้แบบเดิมทั้งหมด |
| การตัดประโยคย่อยจะช่วยได้มาก | ช่วยแค่ +0.016 เพราะคำขัดแย้งโผล่แค่ 15% ของรีวิว |
| multi-label เพียว ๆ จะทำให้ข้อมูลแย่ลง | รอบแรกวัดแล้วไม่ต่าง เพราะชุดประเมินเป็นคำชม 88% จนกลุ่มที่ต่างมีน้อยเกินไป — ต้องเก็บข้อมูลเพิ่มถึงจะพิสูจน์ได้ (รอบสองพิสูจน์ได้จริง) |
| หมวด 2 แย่เพราะข้อมูลน้อย | แย่เพราะ**คู่มือขัดกันเอง** บรรทัดหนึ่งบอก "ไหว้พระ → หมวด 10" อีกสองข้อบอกให้ใช้หมวด 2 |

### อันดับ 3 — การออกแบบให้ของเดิมไม่พังระหว่างเปลี่ยนโครงสร้าง

ตอนย้ายไป multi-aspect ต้องเพิ่มตาราง เพิ่มคอลัมน์ ย้ายข้อมูล 113,643 แถว
และวิเคราะห์ใหม่ 70,888 รีวิว โดยที่หน้าเว็บกับรายงานเดิมต้องทำงานต่อได้ตลอด

วิธีที่ใช้คือ **เพิ่มอย่างเดียว ไม่แก้ของเดิมสักคอลัมน์** —
`sentiment` และ `pain_point_category` ยังมีค่าเดิมครบ ส่วนของใหม่ไปอยู่ใน
`overall_sentiment`, `primary_category_id` และตาราง `review_aspects`
ผลคือมีตัวเลขสองชุดบนหน้าเดียวกันชั่วคราว ซึ่งต้องเขียนคอมเมนต์กำกับว่าตั้งใจ

## 7. สิ่งที่ต่างจากแบบที่วางไว้ตอนแรก

### 7.1 วิธีจัดหมวด: LDA → WangchanBERTa

**แบบเดิม** ใช้ LDA แยกหัวข้อแบบไม่มีผู้สอน (เห็นได้จาก commit `update_cafe_backup_LDA`
และ `Add DB seed + drill-down + cleanup LDA`)

**ปัญหา** หัวข้อที่ LDA ได้ไม่ตรงกับหมวดที่คนเข้าใจ และตั้งชื่อหมวดเองไม่ได้
ทำให้เอาไปสื่อสารกับผู้ประกอบการไม่ได้

**แบบที่ใช้จริง** ให้ Claude ติดป้ายหมวดตามรายการที่กำหนดเอง แล้วกลั่นความรู้
ลงมาที่ WangchanBERTa (knowledge distillation) เพื่อให้รันเองได้ฟรีโดยไม่ต้องเรียก API

### 7.2 โครงสร้างผล: 1 รีวิว 1 หมวด → หลายหมวดพร้อมอารมณ์รายหมวด

**แบบเดิม** `analyzed_reviews.review_id` เป็น `unique` → เก็บได้รีวิวละ 1 หมวด 1 อารมณ์

**ปัญหาที่วัดได้** ชุด gold บอกว่าจริง ๆ แล้ว **1.96 หมวด/รีวิว** โมเดลเดิมจึงมี
recall แค่ 0.407 และ 13.1% ของรีวิวมีหมวดที่อารมณ์ไม่เหมือนกัน เช่น
"อาหารอร่อยแต่ที่จอดรถน้อย" ซึ่งการใช้อารมณ์เดียวกับทุกหมวดทำให้หมวดที่ถูก**ชม**
ถูกนับเป็นคำบ่น

**แบบที่ใช้จริง** ตาราง `review_aspects` (PK = `review_id` + `category_id`)
พร้อมโมเดลสองตัว: จำแนกหมวดแบบ multi-label และทำนายอารมณ์รายหมวด (ABSA)

### 7.3 ชุดหมวด: 12 หมวด → 11 หมวด

ยุบ "ข้อมูลและป้ายบอกทาง" เข้ากับ "การเดินทาง/ที่จอดรถ" และยุบ "ความปลอดภัย"
เข้ากับ "สิ่งอำนวยความสะดวก" แล้วเพิ่มหมวดใหม่ "สถานที่ท่องเที่ยว กิจกรรม และสินค้า"
ซึ่งเดิมไม่มีหมวดรองรับ ทำให้รีวิววัด อุทยาน พิพิธภัณฑ์ ตลาด ไปกองอยู่ผิดที่

### 7.4 ที่มาของอารมณ์: จำนวนดาว → ข้อความ

**แบบเดิม** มีเส้นทาง `rating-only` ที่เดาอารมณ์จากจำนวนดาว (16,476 แถว)
ซึ่งเท่ากับสอนให้โมเดลเลียนแบบกฎดูดาว ไม่ได้เรียนรู้ภาษา

**แบบที่ใช้จริง** `prepare_data.py` มี `TRUSTED_SOURCES` ที่ตัดเส้นทางนั้นออก
จากชุดเทรนอารมณ์โดยเฉพาะ และกติกาข้อ 7 ระบุชัดว่า
**ตัดสินจากข้อความที่เขียน ไม่ใช่จากจำนวนดาว**

### 7.5 แหล่งป้ายชุดสุดท้าย: จ่ายค่า API → ติดป้ายในเซสชัน

**แผนเดิม** ยิง Claude API ติดป้าย multi-aspect ประมาณ 10,000 รีวิว (~$5–6)

**ที่ทำจริง** ติดป้าย 996 รีวิวในเซสชันการทำงาน โดยเลือกตัวอย่างให้ตรงช่องว่าง
ที่วัดเจอ (รีวิว 1–3 ดาว และหมวดที่ตัวอย่างน้อย) แทนการสุ่มล้วน
**ค่าใช้จ่าย API รวม $0** และได้ผลดีกว่าเป้าที่ตั้งไว้

### 7.6 กราฟสัดส่วนรายหมวด: วงกลม → แท่งซ้อน

วงกลมสื่อว่าส่วนย่อยรวมกันเป็น 100% ซึ่งไม่จริงเมื่อ 1 รีวิวอยู่ได้หลายหมวด
(ผลรวมจริง 192.8%) จึงเปลี่ยนเป็นแท่งซ้อน 👍😐👎 พร้อมสลับสองโหมด
และติดข้อความกำกับใต้กราฟถาวร

## 8. บทเรียนที่เอาไปใช้ต่อได้

1. **มีแหล่งความจริงเดียวเสมอ** รายชื่อหมวด นิยามป้าย ตัวกรอง SQL —
   ทุกอย่างที่ถูก copy ไปสองที่ จะเพี้ยนจากกันในที่สุด

2. **เพิ่ม อย่าแก้** เวลาเปลี่ยนโครงสร้างข้อมูลที่มีของเดิมใช้งานอยู่
   เพิ่มคอลัมน์/ตารางใหม่แล้วให้โค้ดใหม่อ่านของใหม่ ปลอดภัยกว่าการแก้ของเดิม

3. **รายงาน baseline คู่กับผลเสมอ** ตัวเลขเดี่ยว ๆ บอกอะไรไม่ได้
   accuracy 0.92 ที่ไม่มี baseline 0.88 กำกับ คือการรายงานที่ชวนเข้าใจผิด

4. **ตรวจข้อมูลรั่วก่อนรายงานทุกครั้ง** โดยเฉพาะเมื่อชุดประเมินถูกสุ่ม
   มาจากฐานเดียวกับชุดเทรน

5. **วัดก่อนลงมือย้าย** การจำลองด้วยวิธีหยาบ ๆ ก่อน (regex, โมเดลที่มีอยู่)
   ช่วยประหยัดเวลาได้มาก และบางครั้งก็บอกว่าไม่ต้องย้ายเลย

6. **ป้ายที่มาจาก AI ตัวเดียวกันทั้งชุดเทรนและชุดประเมิน ต้องมีคนตรวจ**
   ไม่งั้นจะไม่รู้ว่าเพดานความแม่นอยู่ตรงไหน — ข้อนี้ยังค้างอยู่
