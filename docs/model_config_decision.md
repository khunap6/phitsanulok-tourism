# config ของโมเดลที่ใช้จริง และเหตุผลที่เลือก

ปรับปรุง 2026-10-12 · ทุกตัวเลขในหน้านี้มาจาก `nlp/train/run_seed_sweep.py`
รัน 3 seed ต่อ config ไม่ใช่ตัวเลขจากการรันครั้งเดียว

---

## 1. config ที่ใช้

| โมเดล | สคริปต์ | epoch | lr | batch | seed ที่ประกาศ |
|---|---|---|---|---|---|
| หมวด (multi-label) | `train_multilabel.py` | **16** | 2e-5 | 16 | 20261012 |
| อารมณ์รายหมวด (ABSA) | `train_aspect_sentiment.py` | **12** | 2e-5 | 16 | 20261012 |
| อารมณ์รวม | `train_overall_sentiment.py` | **12** | 2e-5 | 16 | 20261012 |

คำสั่งที่ทำซ้ำได้

```bash
uv run python nlp/train/train_multilabel.py --seed 20261012 --epochs 16
uv run python nlp/train/train_aspect_sentiment.py --seed 20261012 --epochs 12
uv run python nlp/train/train_overall_sentiment.py --seed 20261012 --epochs 12
uv run python nlp/train/evaluate_multiaspect.py
```

⚠️ `--seed` ตรึง **รอบการเทรน** (ค่าเริ่มต้นของหัวจำแนก ลำดับ batch dropout)
ไม่ใช่ส่วนแบ่ง train/val ซึ่งตรึงด้วยค่า `SEED` ในสคริปต์และ **ต้องไม่เปลี่ยน**
ถ้าเปลี่ยน ตัวเลขทุกค่าที่เคยรายงานจะเทียบกันไม่ได้

⚠️ `about.json` และ `thresholds.json` ของโมเดลแต่ละตัวบันทึก `run_seed`
คู่กับ `epochs`/`lr`/`batch_size`/`max_length` ไว้ ให้ดูที่นั่นเป็นหลักว่า
โมเดลบนดิสก์มาจาก config ไหน

## 2. ทำไมโมเดลหมวดใช้ 16 epoch

เทียบ 3 config ด้วย seed ชุดเดียวกัน (20261012, 1, 2)

| หมวด micro-F1 | 8 epoch | 16 epoch | 24 epoch |
|---|---|---|---|
| seed 20261012 | 0.8640 | 0.8805 | 0.8842 |
| seed 1 | 0.8091 | 0.8642 | **0.8461** |
| seed 2 | 0.8616 | 0.8866 | 0.8934 |
| **mean ± sd** | 0.8449 ± 0.0310 | **0.8771 ± 0.0116** | 0.8746 ± 0.0251 |

| | 8 → 16 | 16 → 24 |
|---|---|---|
| หมวด micro-F1 | +0.032 **เกิน sd** | −0.003 อยู่ในช่วง sd |
| หมวด recall | +0.050 **เกิน sd** | +0.003 อยู่ในช่วง sd |
| ทั้งระบบ micro-F1 | +0.032 **เกิน sd** | −0.007 อยู่ในช่วง sd |
| sd ของ micro-F1 | 0.0310 → 0.0116 ดีขึ้น | 0.0116 → 0.0251 **แย่ลงเท่าตัว** |

**สรุป** 8 → 16 ดีขึ้นจริงเกินความผันผวน แต่ 16 → 24 ไม่ดีขึ้นเลยและเสถียรน้อยลง
seed 1 ตกจาก 0.8642 เหลือ 0.8461 แสดงว่าเลย 16 ไปแล้วเริ่มไม่คุ้ม
จึงเลือก 16 ซึ่งทั้งดีที่สุด เสถียรที่สุด และถูกกว่า 24 อยู่ 1/3

## 3. ทำไมโมเดลอารมณ์รายหมวดใช้ 12 epoch

| อารมณ์รายหมวด macro-F1 | 12 epoch | 16 epoch |
|---|---|---|
| seed 20261012 | 0.6727 | 0.7027 |
| seed 1 | 0.6825 | **0.6404** |
| seed 2 | 0.6611 | 0.7010 |
| **mean ± sd** | 0.6721 ± 0.0107 | 0.6814 ± 0.0355 |

ต่างกัน +0.009 ซึ่ง **อยู่ในช่วง sd** และรายตัว seed สลับทิศกัน
(+0.030, −0.042, +0.040) จึงไม่มีหลักฐานว่า 16 ดีกว่า

⚠️ กติกาที่ใช้ตัดสิน เมื่อผลต่างไม่เกิน sd ให้ถือว่า **เท่ากัน**
ไม่ใช่ "ดีกว่าเล็กน้อย" แล้วเลือกตัวที่ถูกกว่าหรือเร็วกว่า → 12 epoch
ถ้าเลือกตามค่าเฉลี่ยที่สูงกว่าทุกครั้ง จะกลายเป็นการจูนให้เข้ากับ
ความผันผวนของชุดประเมิน ไม่ใช่การปรับปรุงจริง

## 4. ข้อควรระวังเวลาอ่านตัวเลขของโปรเจกต์นี้

**1. ผลต่างระดับ 0.01–0.03 อ่านเป็นการปรับปรุงไม่ได้**
ชุดประเมินมี 251 รีวิว / 493 คู่ ที่ config ปิดท้าย sd ของหมวด micro-F1
อยู่ที่ ±0.0116 และ macro-F1 ±0.0174

**2. F1 รายหมวดแกว่งหนักกว่านั้นมาก** หมวดที่มีตัวอย่างใน gold ไม่ถึง 20 รายการ

| หมวด | gold | sd ที่วัดได้ (8 ep) |
|---|---|---|
| 7 การเดินทาง | 17 | ±0.2074 |
| 2 ความคิดเห็นทั่วไป | 14 | ±0.1406 |
| 8 ความแออัด | 11 | ±0.1168 |
| 6 ความสะอาด | 16 | ±0.0809 |

ค่าเหล่านี้ห้ามนำไปสรุปเชิงสถิติ ต้องติดป้าย "ข้อมูลน้อย" กำกับเสมอ

**3. baseline ส่วนใหญ่ก็แกว่ง** baseline 3 ใน 4 ตัวคำนวณจากผลของโมเดล
(เอาหมวดคะแนนสูงสุดตัวเดียว / ใช้อารมณ์รวมกับทุกหมวด) จึงต้องรายงานเป็น
mean ± sd เหมือนกัน มีแต่ baseline "ทายบวกหมด" ที่นิ่งจริง
`run_seed_sweep.py` เตือนให้เองถ้า baseline ตัวนั้นไม่นิ่ง เพราะถ้าไม่นิ่ง
แปลว่าชุดประเมินเปลี่ยนระหว่างรอบ = มีบั๊ก

**4. ที่มาของ config เดิมสืบไม่ได้** โมเดลรุ่นก่อนหน้าไม่ได้บันทึก seed
และ hyperparameter ไว้ ตัวเลขที่เคยรายงานว่า 0.8963 / 0.8862 / 0.7322 / 0.5933
จึงย้อนทำซ้ำไม่ได้และต้องทิ้ง เรื่องนี้เขียนไว้ละเอียดในหัวข้อ 6.1 ของ
`docs/project_retrospective.md`

## 5. ข้อจำกัดของวิธีเลือก config นี้เอง

1. **3 seed ต่อ config ยังน้อย** sd ที่ได้เป็นค่าประมาณคร่าว ๆ และ sd ของ sd
   เองก็ใหญ่ ถ้ามีเวลาควรเพิ่มเป็น 5–10 seed
2. **เกณฑ์ "เกิน sd" ไม่ใช่การทดสอบนัยสำคัญทางสถิติ** ด้วย n=3 ต่อชุด
   t-test ก็ยังไม่มีกำลังพอ เกณฑ์นี้ใช้กันตัวเองเผลอสรุปเท่านั้น
3. **จูนแค่ epoch** ไม่ได้จูน lr, batch size, max length, pos_weight หรือ
   threshold strategy ซึ่งอาจให้ผลมากกว่า epoch
4. **ส่วนแบ่ง train/val คงที่ตลอด** ความผันผวนที่วัดได้จึงเป็นของการเทรนเท่านั้น
   ยังไม่ได้วัดความผันผวนของการแบ่งข้อมูล ซึ่งต้องทำ cross-validation
5. **เลือก config บนชุด gold ที่ใช้รายงานผลด้วย** ตรงนี้คือการรั่วแบบอ่อน ๆ
   (model selection on the test set) ตัวเลขที่รายงานจึงมีแนวโน้มสูงกว่าความจริง
   เล็กน้อย ทางที่ถูกคือแบ่งชุด dev ออกมาอีกชุด แต่ gold มีแค่ 251 รีวิวสะอาด
   จึงยังแบ่งไม่ได้ **ข้อนี้ต้องระบุในเล่ม**
