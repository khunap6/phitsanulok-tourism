# สไลด์ 15 — ขั้นตอนการพัฒนาระบบและรวบรวมข้อมูล

## เนื้อหาที่ควรใส่ในกล่อง "เกณฑ์การเตรียมข้อมูล"

| เกณฑ์ | เหตุผล | ผลที่เกิดกับข้อมูล |
|---|---|---|
| กันรีวิวซ้ำด้วย `text_hash` | รีวิวเดียวถูกเก็บซ้ำได้ถ้า scroll ทับกัน | คีย์คือ (place_id, text_hash) |
| แยกรีวิวที่ไม่มีข้อความออกจากการวิเคราะห์ | ให้ดาวอย่างเดียว ไม่มีข้อความให้ NLP อ่าน | 41,282 จาก 114,295 (36.1%) |
| ไม่ลบรีวิวที่ไม่มีข้อความทิ้ง | ยังใช้คำนวณคะแนนดาวเฉลี่ยได้ | เก็บไว้ครบในฐานข้อมูล |
| คัดสถานที่นอกขอบเขตงานวิจัย | ร้านซ่อมรถ ธนาคาร โรงพยาบาล ไม่ใช่แหล่งท่องเที่ยว | 762 → 719 แห่ง |
| แยกสถานะร้านเปิด/ปิด | ร้านที่ปิดแล้วไม่สะท้อนสภาพปัจจุบัน | 719 → 694 แห่ง |
| ไม่ตัดข้อความสั้น | "อร่อย" เป็นความเห็นจริงของคน | 4,001 รายการสั้นกว่า 10 อักขระ ยังอยู่ |

⚠️ **ข้อสุดท้ายสำคัญ** ถ้าตัดข้อความสั้นออกจะทำให้ตัวส่วนของทุกสัดส่วนเปลี่ยน
และกลายเป็นการเลือกเฉพาะข้อมูลที่เข้าทาง

## ตัวเลขของแต่ละขั้น

| ขั้น | ทำอะไร | ตัวเลขจริง |
|---|---|---|
| 1 กำหนดสถานที่ | Google Places API · Nearby Search 7 ประเภท · แบ่งพื้นที่เป็นเซลล์รัศมี 1 กม. | 885 เซลล์ · พบ 8,147 รายการ · คัดเหลือ **762 แห่ง** |
| 2 รวบรวมรีวิว | Playwright (Selenium สำรอง) เปิดหน้าสถานที่แล้วเลื่อนอ่านรีวิว | **114,295 รีวิว** ช่วง 2554–2569 |
| 3 ตรวจสอบข้อมูล | กันซ้ำด้วย hash · ตรวจพิกัด · คัดนอกขอบเขต | ในขอบเขต **719** · เปิดอยู่ **694** |
| 4 ทำความสะอาด | ตัดไอคอน ข้อความ UI และคำที่ไม่เกี่ยวข้อง | มีข้อความให้วิเคราะห์ **73,013** |
| 5 จัดเก็บชุดข้อมูล | PostgreSQL 16 + PostGIS | 13 ตาราง · เก็บพิกัดเป็น geometry |

## สคริปต์พูด สไลด์ 15 (ประมาณ 90 วินาที)

> ขั้นตอนการเตรียมข้อมูลแบ่งเป็น 5 ขั้นครับ
>
> **ขั้นแรก กำหนดสถานที่** ผมใช้ Google Places API ค้นหาแบบ Nearby Search
> โดยแบ่งพื้นที่จังหวัดเป็นเซลล์รัศมี 1 กิโลเมตร แล้วค้นทีละเซลล์ด้วย 7 ประเภทสถานที่
> ได้รายการมา 8,147 รายการ แล้วคัดเหลือ 762 แห่งที่เก็บรีวิวจริง
>
> **ขั้นที่สอง รวบรวมรีวิว** ใช้ Playwright เปิดหน้าสถานที่แล้วเลื่อนอ่านรีวิว
> เก็บได้ 114,295 รีวิว ครอบคลุมตั้งแต่ปี 2554 ถึง 2569
>
> **ขั้นที่สาม ตรวจสอบข้อมูล** กันรีวิวซ้ำด้วยการแฮชข้อความ
> และคัดสถานที่ที่ไม่ใช่แหล่งท่องเที่ยวออก เช่น ธนาคาร โรงพยาบาล ร้านซ่อมรถ
> เหลือ 719 แห่งในขอบเขต และ 694 แห่งที่ยังเปิดกิจการ
>
> **ขั้นที่สี่ ทำความสะอาด** ตัดไอคอนและข้อความส่วนติดต่อผู้ใช้ที่ติดมากับการดึงข้อมูล
> จากทั้งหมดมีรีวิวที่มีข้อความให้วิเคราะห์ 73,013 รีวิว
> อีก 41,282 รีวิวเป็นการให้ดาวอย่างเดียวโดยไม่เขียนอะไร คิดเป็น 36 เปอร์เซ็นต์
>
> **ขั้นสุดท้าย จัดเก็บ** ลง PostgreSQL ที่ติดตั้งส่วนขยาย PostGIS เพื่อเก็บพิกัดและคิวรีเชิงพื้นที่ได้
>
> **จุดที่อยากเน้น** คือรีวิวที่ให้ดาวอย่างเดียวผมไม่ได้ลบทิ้ง แต่แยกออกจากการวิเคราะห์ข้อความ
> เพราะถ้าเอามานับเป็นตัวส่วนของสัดส่วนปัญหา จะทำให้ตัวเลขต่ำกว่าความจริง
> ตรงนี้เคยวัดแล้วว่าทำให้ยอดปัญหาระดับสูงเปลี่ยนจริง และทำให้ลำดับร้านสลับกัน

# สไลด์ 16 — สถาปัตยกรรมระบบ

## ⚠️ ผังเดิมในสไลด์ไม่ตรงกับระบบจริง ต้องแก้

ผังเดิมวาดเป็นเส้นเดียว

```
ผู้ใช้ → Frontend → Backend API → AI/NLP Service → Database
```

ผังนี้สื่อว่า **ทุกครั้งที่ผู้ใช้เปิดหน้าเว็บ ระบบจะเรียกโมเดล AI ให้วิเคราะห์สด**
ซึ่ง **ไม่ใช่สิ่งที่ระบบทำ**

**หลักฐานจากโค้ด**
- โฟลเดอร์ `api/` ไม่มีการเรียก `from_pretrained`, `torch` หรือ `transformers` เลยแม้แต่บรรทัดเดียว
- โมเดลถูกโหลดเฉพาะใน `nlp/train/` และ `scripts/reanalyze_multiaspect.py`
- endpoint ทั้งหมดอ่านจากตาราง `analyzed_reviews` และ `review_aspects` ที่เก็บผลไว้ล่วงหน้า
- วัดเวลาโหลดหน้าแดชบอร์ดได้ 4.0 วินาที ซึ่งเป็นไปไม่ได้ถ้าต้องรันโมเดลกับรีวิวหลายหมื่นรายการสด ๆ

⚠️ **ถ้าปล่อยผังเดิมไว้แล้วอาจารย์ถามว่า "กดแล้ว AI ทำงานเลยไหม"
คำตอบที่ถูกคือไม่ ซึ่งจะขัดกับผังที่ฉายอยู่**

## ผังที่ตรงกับความจริง — แบ่งเป็น 2 ส่วน

```
┌─ ส่วนที่ 1 · ประมวลผลล่วงหน้า (ทำเป็นรอบ ไม่ได้ทำตอนผู้ใช้เปิดเว็บ) ─┐

  Google Maps ──► Scraper ──► ฐานข้อมูล ──► AI / NLP Service ──┐
                 (Playwright)   (รีวิวดิบ)   (WangchanBERTa 3 โมเดล)  │
                                                                      │
                                              เขียนผลวิเคราะห์กลับ ◄──┘
                                              (analyzed_reviews,
                                               review_aspects)

┌─ ส่วนที่ 2 · ตอบคำขอผู้ใช้ (เรียลไทม์) ────────────────────────────┐

  ผู้ใช้ / นักวิจัย ──► Frontend ──► Backend API ──► Database
                        (React)      (FastAPI)      (PostgreSQL
                                                     + PostGIS)
                                     ◄── อ่านผลที่วิเคราะห์ไว้แล้ว
```

**ประโยคเดียวที่อธิบายได้ทั้งผัง**
AI อยู่ในสายการเตรียมข้อมูล ไม่ได้อยู่ในสายการตอบคำขอ

## เนื้อหาสำหรับกล่อง "คำอธิบายสถาปัตยกรรม"

> ระบบแบ่งเป็นสองส่วนที่ทำงานคนละเวลา
>
> **ส่วนประมวลผลล่วงหน้า** scraper ดึงรีวิวจาก Google Maps เก็บลงฐานข้อมูล
> จากนั้นโมเดล WangchanBERTa 3 ตัววิเคราะห์หมวดและอารมณ์ แล้วเขียนผลกลับลงฐานข้อมูล
> ขั้นนี้ทำเป็นรอบเมื่อมีข้อมูลใหม่ ไม่ได้ทำตอนผู้ใช้เปิดเว็บ
>
> **ส่วนตอบคำขอ** เมื่อผู้ใช้เปิดแดชบอร์ด React เรียก FastAPI
> ซึ่งคิวรีผลวิเคราะห์ที่เก็บไว้แล้วจากฐานข้อมูลส่งกลับไปแสดงผล
> ไม่มีการเรียกโมเดล AI ในขั้นนี้ ทำให้ตอบสนองได้ภายใน 4 วินาที

## โมเดล 3 ตัวที่ใช้

| โมเดล | หน้าที่ | ผลลัพธ์ |
|---|---|---|
| จัดหมวดแบบ multi-label | 1 รีวิวพูดถึงได้หลายหมวดพร้อมกัน | 11 หมวด |
| อารมณ์รายหมวด (ABSA) | ป้อนเป็นคู่ (ชื่อหมวด, ข้อความ) ตอบอารมณ์ต่อหมวดนั้น | ชม / กลาง ๆ / ติ |
| อารมณ์รวมของรีวิว | อารมณ์โดยรวมของทั้งรีวิว | ชม / กลาง ๆ / ติ |

⚠️ ทั้งสามตัวเป็น WangchanBERTa ที่ fine-tune ด้วยวิธี knowledge distillation
ให้ Claude ติดป้ายตัวอย่าง 947 รีวิวเป็นชุดสอน แล้วเทรนโมเดลจากป้ายนั้น
**ตอนใช้งานจริงไม่เรียก API ภายนอกเลย ค่าใช้จ่ายต่อรีวิวเป็นศูนย์**

## สคริปต์พูด สไลด์ 16 (ประมาณ 90 วินาที)

> สถาปัตยกรรมระบบแบ่งเป็นสองส่วนที่ทำงานคนละเวลาครับ
>
> **ส่วนแรกคือการประมวลผลล่วงหน้า** scraper ดึงรีวิวจาก Google Maps
> เก็บลงฐานข้อมูลเป็นรีวิวดิบก่อน จากนั้นโมเดล NLP สามตัวจะอ่านรีวิวเหล่านั้น
> แล้ววิเคราะห์ว่าแต่ละรีวิวพูดถึงหมวดอะไรบ้าง และมีอารมณ์อย่างไรต่อแต่ละหมวด
> ผลที่ได้เขียนกลับลงฐานข้อมูล ขั้นตอนนี้ทำเป็นรอบ ไม่ได้ทำตอนผู้ใช้เปิดเว็บ
>
> **ส่วนที่สองคือการตอบคำขอผู้ใช้** เมื่อเปิดแดชบอร์ด หน้าเว็บที่เขียนด้วย React
> จะเรียก Backend API ที่เขียนด้วย FastAPI ซึ่งคิวรีผลวิเคราะห์ที่เก็บไว้แล้ว
> จากฐานข้อมูล PostgreSQL ส่งกลับไปแสดงเป็นกราฟ
>
> **จุดที่อยากชี้แจง** คือ AI ไม่ได้อยู่ในเส้นทางการตอบคำขอครับ
> ตอนผู้ใช้กดดูข้อมูล ระบบไม่ได้เรียกโมเดลให้วิเคราะห์ใหม่ แต่อ่านผลที่วิเคราะห์ไว้แล้ว
> ออกแบบแบบนี้เพราะการรันโมเดลกับรีวิวเจ็ดหมื่นรายการใช้เวลานานเกินกว่าจะทำสดได้
> ผลคือหน้าแดชบอร์ดโหลดเสร็จภายใน 4 วินาที
>
> ข้อแลกเปลี่ยนคือเมื่อมีรีวิวใหม่เข้ามา ต้องรันขั้นวิเคราะห์ใหม่ก่อนตัวเลขบนหน้าเว็บจึงจะอัปเดต
> ไม่ได้อัปเดตทันที

# คำถามที่น่าจะโดนถาม และคำตอบที่ตรวจย้อนได้

### "ทำไมไม่ให้ AI วิเคราะห์สดตอนผู้ใช้กด"
> เพราะมีรีวิวที่ต้องวิเคราะห์ 73,013 รายการ
> การรันโมเดลสดจะใช้เวลาเกินกว่าที่ผู้ใช้จะรอได้
> การวิเคราะห์ล่วงหน้าแล้วเก็บผลทำให้ตอบได้ใน 4 วินาที
> ข้อแลกเปลี่ยนคือข้อมูลไม่ใช่เรียลไทม์

### "ความแม่นของโมเดลเท่าไร"
> วัดบนชุดประเมินที่ติดป้ายแยกต่างหาก
> จัดหมวดได้ micro-F1 0.88 macro-F1 0.75
> และรายงานเป็นค่าเฉลี่ยจากการเทรน 3 ครั้งพร้อมส่วนเบี่ยงเบน
> ไม่ใช่ตัวเลขจากการรันครั้งเดียว

### "ป้ายที่ใช้สอนโมเดลมาจากไหน เชื่อได้ไหม"
> ป้ายมาจาก AI ตามคู่มือที่เขียนไว้ แล้วผมสุ่มตรวจเองแบบปิดตา 95 รายการ
> ได้ค่าความสอดคล้อง Cohen's kappa เท่ากับ 0.78 สำหรับอารมณ์รวม
> และ 0.81 สำหรับอารมณ์รายหมวด ซึ่งอยู่ในเกณฑ์ดีถึงดีมาก
> ค่านี้เป็นเพดานความแม่นที่เป็นไปได้ของโมเดล

### "ทำไมต้องแยกอารมณ์รายหมวด ใช้อารมณ์รวมอย่างเดียวไม่ได้เหรอ"
> เพราะ 13 เปอร์เซ็นต์ของรีวิวมีอารมณ์ไม่เหมือนกันระหว่างหมวด
> เช่น ชมอาหารแต่ติที่จอดรถในรีวิวเดียวกัน
> ถ้าใช้อารมณ์รวมอย่างเดียวจะนับว่าที่จอดรถถูกชมไปด้วย
> วัดแล้วการแยกอารมณ์รายหมวดดีกว่าการใช้อารมณ์รวม 0.70 เทียบ 0.58

### "ข้อมูลครอบคลุมแค่ไหน"
> เก็บได้ 114,295 รีวิวจาก 762 สถานที่
> แต่ไม่ทราบว่าเป็นกี่เปอร์เซ็นต์ของรีวิวที่มีอยู่จริง
> เพราะ Google ไม่แสดงจำนวนทั้งหมดที่เชื่อถือได้
> ประมาณการคร่าว ๆ จากตัวเลขที่ Places API รายงานคือราว 70 เปอร์เซ็นต์
> โดยสถานที่ที่มีรีวิวมากจะเก็บได้สัดส่วนน้อยกว่านั้น

### "เก็บข้อมูลส่วนบุคคลไหม"
> ไม่ครับ ตารางรีวิวมีเพียงคะแนนดาว ข้อความ และวันที่
> ไม่มีคอลัมน์ชื่อผู้รีวิว ไม่มีโปรไฟล์ ไม่มีตัวระบุใด ๆ
> จึงเชื่อมกลับไปหาตัวบุคคลไม่ได้
