## 1. ข้อจำกัดด้านข้อมูลที่เก็บมา

### 1.1 ไม่ทราบความครบถ้วนของการเก็บรีวิว

เก็บรีวิวได้ **114,295** รายการจาก **762** สถานที่ แต่**ไม่ทราบว่าเป็นกี่เปอร์เซ็นต์
ของรีวิวที่มีอยู่จริง** เพราะ Google ไม่แสดงจำนวนรีวิวทั้งหมดที่เชื่อถือได้ และหน้าเว็บ
ส่งข้อมูลมาไม่เท่ากันในแต่ละครั้งที่โหลด

**ผลต่อข้อสรุป** ตัวเลขทุกตัวเป็น "สิ่งที่พบในรีวิวที่เก็บได้" ไม่ใช่ "สิ่งที่คนพิษณุโลก
และผู้มาเยือนคิด" การอ้างว่าเป็นตัวแทนของประชากรทั้งหมดทำไม่ได้

### 1.2 รีวิวส่วนใหญ่เป็น 4–5 ดาว รีวิว 1–3 ดาวมีแค่ 11.81%

| ดาว | จำนวน | มีข้อความ | ร้อยละ |
|---|---|---|---|
| 1 | 3,238 | 2,437 | 2.83% |
| 2 | 2,021 | 1,433 | 1.77% |
| 3 | 8,234 | 4,696 | 7.20% |
| 4 | 24,089 | 14,663 | 21.08% |
| 5 | 76,713 | 49,784 | 67.12% |

**นี่คือข้อจำกัดที่กระทบงานนี้มากที่สุด** เพราะงานนี้ศึกษา *pain point* ซึ่งอยู่ใน
รีวิวดาวน้อยเป็นหลัก แต่กลุ่มนั้นมีเพียง 13,493 รายการ (11.81%)

ผลที่ตามมาเป็นลูกโซ่
- ชุด gold ที่สุ่มมาเป็นคำชม 88% กลุ่มคำติจึงเล็กเกินกว่าจะวัดได้แม่น
- `neutral` และ `negative` มีตัวอย่างน้อย ทำให้ macro-F1 แกว่งแรง
- ไม่ทราบว่าสัดส่วนดาวที่เห็นสะท้อนความจริง หรือเป็นผลของวิธีเก็บ
  (Google จัดลำดับรีวิวที่ "มีประโยชน์" ขึ้นก่อน ซึ่งมักเป็นรีวิวบวก)

**ยังไม่ได้แก้** มีข้อเสนอให้เก็บรีวิว 1–3 ดาวเพิ่มโดยเจาะจง แต่ต้องแก้ scraper
ซึ่งยังไม่ได้รับอนุมัติ

### 1.3 รีวิว 36.1% ไม่มีข้อความ (ให้ดาวอย่างเดียว)

41,282 จาก 114,295 รายการเป็นการให้ดาวโดยไม่เขียนอะไร วิเคราะห์ด้วย NLP ไม่ได้

**แก้แล้ว** ทุกสัดส่วนในระบบกรอง `text_clean <> ''` ทั้งตัวเศษและตัวส่วน
เคยไม่กรองแล้วทำให้ยอดปัญหาระดับสูงพองจาก 1,996 เป็น 2,316 และ**ลำดับร้านสลับจริง**
(ร้านข้าวมันไก่จาก 41 เป็น 52 แซงร้านอื่น)

### 1.4 Google ส่งหน้าเว็บคนละแบบในแต่ละครั้ง

URL เดียวกันส่งได้ 3 แบบ บางแบบจำกัดรีวิวไว้ที่ 5 ใบ ทดสอบโหลดซ้ำ 30 ครั้ง
ได้แบบจำกัดทุกครั้งในช่วงนั้น แล้วช่วงอื่นได้ฟีดเต็ม — **เป็นเรื่องของช่วงเวลา
ไม่ใช่ของ URL** จึงไม่มีทางรับประกันความครบถ้วนในการรันครั้งเดียว

### 1.5 ข้อความสั้นกว่า 10 อักขระ 4,001 แถว

5.5% ของรีวิวที่มีข้อความสั้นกว่า 10 อักขระ ("ดี", "อร่อย", "โอเค")
NLP อ่านได้แต่แยกหมวดได้ยาก เพราะไม่มีบริบทพอ

**ไม่ได้ตัดออก** เพราะเป็นความเห็นจริงของคน และการตัดออกจะเปลี่ยนตัวส่วน
ของทุกสัดส่วน แต่ควรระบุว่าหมวดที่ระบบจัดให้รีวิวกลุ่มนี้มีความแน่นอนต่ำกว่า
(กลุ่มนี้มักถูกจัดเป็นหมวด 2 ความคิดเห็นทั่วไป ซึ่งถูกต้องตามนิยาม)

### 1.6 ข้อความซ้ำข้ามสถานที่ 25,793 แถว

มีข้อความรีวิวซ้ำกันอยู่ใน 5,639 กลุ่ม hash (รวม 25,793 แถว จาก 114,295)
เพราะคีย์กันซ้ำผูกกับ `(place_id, text_hash)` ไม่ใช่ `text_hash` เดียว
รีวิวเดียวกันจึงนับได้หลายครั้งถ้าโผล่ในหลายสาขา

**ผลต่อข้อสรุป** น้ำหนักของข้อความที่ซ้ำสูงกว่าความจริง และเป็นสาเหตุหนึ่งที่ทำให้
เกิดการรั่วระหว่างชุดเทรนกับชุดประเมิน (ดูข้อ 2.3)

### 1.7 ขอบเขตของงานเพิ่งถูกนิยามอย่างเป็นทางการเมื่อ 2026-10-13

**เดิมขอบเขตถูกนิยามไว้ที่เดียว** คือ `PLACE_TYPES` ใน `scripts/discover_api.py`
ซึ่งเป็นรายการ type ที่ใช้ **ค้นหา** (7 ตัว: cafe, restaurant, bakery,
tourist_attraction, museum, park, university) ไม่ใช่เกณฑ์ว่า **เก็บอะไรไว้**

ผลที่ตามมา

- สถานที่ที่เข้ามาทางเส้นทางเก่า (`discovered_by='scrape'`) ไม่ผ่านตัวกรองใดเลย
  **40 จาก 42 แห่งที่อยู่นอกขอบเขตมาจากเส้นทางนี้**
- Google ไม่มี `buddhist_temple` ใน Table 1 วัดจึงค้นด้วย type ไม่ได้
  ทั้งที่วัดพระศรีรัตนมหาธาตุ (833 รีวิว) และพระพุทธชินราช (858)
  เป็นแหล่งท่องเที่ยวหลักที่ `PROJECT_SUMMARY` ระบุชื่อไว้เอง

**แก้แล้ว** `shared/scope.json` (สร้างจาก `scripts/build_scope.py`) นิยามแยก
"ค้นด้วย type อะไร" ออกจาก "นับว่าอยู่ในขอบเขตไหม" พร้อมลำดับตัดสิน 7 ขั้น
และรายการตัดสินรายแห่ง 47 แห่ง ผู้ใช้เป็นคนตัดสินทั้งสามหลักการ

| หลักการ | ผู้ใช้ตัดสิน |
|---|---|
| ตลาด | **อยู่ในขอบเขต** — ดึงดูดผู้คนให้มาใช้เงินและเดินเล่นรับประสบการณ์ |
| ร้านเฉพาะทาง (สตูดิโอ ร้านกล้อง เฟอร์นิเจอร์) | **ไม่อยู่** — ไม่เหมือนคาเฟ่ที่ให้คนมาพักผ่อนและถ่ายรูป |
| สถานที่ในมหาวิทยาลัย | **แยกรายกรณี** — อนุสาวรีย์ พิพิธภัณฑ์ อ่างเก็บน้ำ อยู่ในขอบเขต · ห้องสมุด คณะ หอพัก สนามกีฬา ไม่อยู่ |

**ผลกระทบที่วัดได้** ตัดออก **42 สถานที่ · 1,095 รีวิวที่มีข้อความ (1.50%)
· 1,824 การกล่าวถึงรายหมวด (1.29%)**

**⚠️ ตัวเลขทุกตัวที่รายงานก่อน 2026-10-13 คำนวณบนชุดที่มีของนอกขอบเขตปนอยู่**
รวมถึง kappa ของคน 0.8156 และ micro-F1 ของโมเดล 0.8816 ± 0.0080
ชุด gold v2 สะอาด 251 รีวิวมีรีวิวนอกขอบเขต **4 แถว (1.6%)** และชุด gold v3.1
มี **15 แถว (7.7%)** ซึ่งถูกตัดออกแล้วในชุด v3.2

**ข้อจำกัดที่ยังอยู่** การจัดขอบเขตใช้ `google_types` เป็นหลัก แต่ **33 แห่ง
(1,346 รีวิว) ไม่มี types ใช้ได้เลย** (มีแค่ `establishment,point_of_interest`
หรือ NULL) เพราะเส้นทาง `scrape` เก่าไม่ได้ดึง types จาก API
ต้องใช้ป้ายภาษาไทย `google_category` เป็นทางสำรอง ซึ่งหยาบกว่า

### 1.8 ค้นด้วยชื่อร้านแล้วได้รีวิวของสาขาอื่น

ร้านที่มีหลายสาขาหรือชื่อคล้ายกัน การค้นด้วยชื่อทำให้ได้รีวิวผิดร้าน
แก้ด้วยการยึด `place_id` จาก Google เป็นหลัก แต่**ข้อมูลที่เก็บมาก่อนการแก้
อาจมีรีวิวปนอยู่** และไม่มีทางย้อนตรวจได้ว่ากี่แถว

### 1.9 สถานที่ปิดกิจการ 25 แห่ง

ร้านเปิด 737 · ปิดชั่วคราว 17 · ปิดถาวร 8 รีวิวของร้านที่ปิดยังอยู่ในฐานข้อมูล
endpoint มี `status` ให้กรองได้ แต่ **ค่าตั้งต้นของแต่ละ endpoint ไม่เหมือนกัน**
(บางตัว `operational` บางตัว `all` เพื่อไม่ให้ผู้เรียกเดิมได้ผลต่างไป)
ถ้าเอาตัวเลขจากสอง endpoint มาวางข้างกันโดยไม่ส่ง `status` เหมือนกัน จะเทียบกันไม่ได้

### 1.10 เนื้อรีวิวถูกตัดที่ 500 อักขระโดยโค้ดเก็บข้อมูลเอง

ไม่ใช่ข้อจำกัดของ Google แต่เป็นของเราเอง มีการตัดสามชั้นต่อกัน

| จุด | การตัด |
|---|---|
| `scraper/scraper_core.py:692` | `text.substring(0, 600)` ชั้น JS ตัวหลัก |
| `scraper/scraper_core.py:834` | `body.substring(0, 600)` ชั้นสำรอง |
| `scraper/scraper_core.py:1470` | `text[:500]` ตัวที่ลงฐานข้อมูล |

วัดได้ **81 แถวที่ `LENGTH(text) = 500` พอดี** เทียบกับ 18 แถวในช่วง 490-499
การกองที่ค่าสูงสุดแบบนี้คือลายเซ็นของการตัดแข็ง ไม่ใช่การกระจายตามธรรมชาติ
คิดเป็น **0.071%** ของรีวิวที่มีข้อความ (81 / 114,295)

อ่านข้อความทั้ง 81 แถวแล้ว **ส่วนที่ถูกตัดคือคำตอบจากเจ้าของร้านที่ต่อท้าย
ไม่ใช่คำของผู้รีวิว** (`text_clean` ของ 81 แถวนั้นยังได้ 151-332 อักขระ)
ความเสียหายต่อการวิเคราะห์ pain point จึงเกือบเป็นศูนย์

**ทำไมไม่เก็บใหม่** `text_hash = md5(clean_review_text(text))` ถ้า `text` เปลี่ยน
hash จะเปลี่ยนทั้งก้อน แล้วรีวิวเดิมทุกใบจะถูก INSERT ซ้ำเป็นแถวใหม่
(บั๊กเดียวกับที่เคยทำให้มีรีวิวซ้ำ 3,453 แถว) ต้นทุนสูงกว่าประโยชน์มาก
**ตัดสินใจเมื่อ 2026-10-13 บันทึกเป็นข้อจำกัด ไม่แก้ scraper**

### 1.11 ตรวจแล้วว่าเนื้อรีวิวไม่ได้ถูกตัดเพราะ scraper ไม่กดปุ่มเพิ่มเติม

เป็นผลเชิงลบที่บันทึกไว้เพราะเป็นคำถามที่ถูกถามซ้ำได้

**ข้อเท็จจริงที่ยืนยันแล้ว** scraper ไม่เคยกดปุ่มเพิ่มเติมระดับรีวิวจริง
มีแต่ `ดูรีวิวเพิ่มเติม` ซึ่งเป็นปุ่มระดับฟีด และ `/^เพิ่มเติม$/`
ที่ `scraper/scraper_core.py:760` อยู่ในรายการ**ทิ้งบรรทัด** ไม่ใช่กดปุ่ม

**แต่เนื้อรีวิวไม่หาย** เพราะ Google ใส่ข้อความเต็มไว้ใน DOM อยู่แล้ว
ปุ่มนั้นกางบล็อก metadata (`ประเภทการสั่ง` · `รับประทานที่ร้าน` · `อาหาร: 5`)
ซึ่งเป็นเหตุที่ป้ายพวกนี้เท่านั้นที่ถูกตัดห้วน (`ประเภทก` · `รับประทานที่ร`)

หลักฐานสามชั้น

| การทดสอบ | ผล |
|---|---|
| อัตราเนื้อถูกตัดตามความยาว | 120-199 อักขระ 0.8% · 200-399 อักขระ 0.7% — **ตกลง** ไม่พุ่งขึ้น ถ้าตัดตามความยาวต้องเป็น ~100% |
| รีวิวยาว 200-300 อักขระที่เนื้อครบ | 4,777 ใบ ในนั้น **80.4% มีปุ่มเพิ่มเติม** — ปุ่มมีอยู่แต่เนื้อครบ |
| มีรีวิวที่ดิบยาวถึง 500 อักขระ | 81 ใบ ถ้า Google ตัด DOM จริงจะไม่มีทางได้ถึง 500 |

และจุดไข่ปลาเป็นอักขระที่ผู้รีวิวพิมพ์เองด้วย `text_clean` ที่มีจุดไข่ปลา
มี 765 ใบ ในนั้น **755 ใบมีจุดไข่ปลาอยู่กลางข้อความ** ไม่ใช่ท้าย
บวกที่พิมพ์เป็นจุดสามจุดอีก 909 ใบ

**สิ่งที่ยังพิสูจน์ไม่ได้** ยืนยันไม่ได้ว่า Google ไม่ตัดรีวิวที่ยาวเกิน 600 อักขระ
เพราะโค้ดเราตัดก่อนถึงจุดนั้น (ดู 1.10) เนื้อที่ยาวสุดในฐานคือ 382 อักขระ
ซึ่งอาจเป็นเพดานของเราเอง ไม่ใช่ของ Google ต้องมี ground truth จากข้างนอก
(Places API หรือเปิดหน้าจริง) ถึงจะปิดช่องนี้ได้ **ยังไม่ได้ทำ**

## 2. ข้อจำกัดด้านป้าย (labels)

### 2.1 ป้ายทั้งหมดมาจาก AI ไม่มีคนตรวจ — ข้อจำกัดใหญ่ที่สุดของงาน

| ชุด | จำนวน | ที่มาของป้าย |
|---|---|---|
| ชุดประเมิน (gold) | 300 รีวิว (ใช้ได้ 251) | Claude ตามคู่มือ |
| ชุดเทรน (silver) | 996 รีวิว / 1,884 คู่ | Claude คนละรอบ คนละชุด |
| ข้อมูลที่เหลือ | 112,795 รีวิว | โมเดลที่เทรนจาก silver |

**ผลที่ตามมา** ตัวเลขทุกตัวในงานนี้วัด **ความสอดคล้องกับป้ายที่ Claude ติด**
ไม่ใช่ความถูกต้องสัมบูรณ์ ถ้า Claude ติดป้ายผิดอย่างเป็นระบบ โมเดลจะผิดตามแบบเดียวกัน
แล้วคะแนนจะยังสูง — ความสอดคล้องสูงอาจหมายถึง "ผิดเหมือนกัน" ไม่ใช่ "ถูกทั้งคู่"

**ยังไม่ได้ทำ** เตรียมชุดให้คนตรวจ 100 รายการไว้แล้วที่
`reports/evaluation/human_check_blank.csv` (ยังว่างทั้งไฟล์) เมื่อกรอกแล้ว
รัน `uv run python scripts/human_check.py --score` จะได้ Cohen's kappa
ซึ่งเป็นตัวบอก **เพดานความแม่นที่เป็นไปได้** ของทั้งงาน

**จนกว่าจะทำข้อนี้ ตัวเลขความแม่นทุกตัวยังไม่มีเพดานอ้างอิง**

### 2.2 ชุดเทรนและชุดประเมินมาจากแหล่งเดียวกัน

ทั้งสองชุดติดโดย Claude (คนละรอบ คนละคู่มือเวอร์ชัน แต่โมเดลเดียวกัน)
จึงไม่เป็นอิสระต่อกันอย่างแท้จริง

### 2.3 เคยมีข้อมูลรั่วระหว่างชุดเทรนกับชุดประเมิน 49 รายการ

ตรวจพบว่าชุด gold 300 รายการมีข้อความซ้ำกับชุดเทรนของโมเดลรุ่นเดิม **49 รายการ**
(42 รายการซ้ำตรง + 12 รายการที่โผล่ในหลายชุด นับทับกัน)

**แก้แล้ว** ตัด 49 รายการนั้นออกจากการประเมิน เหลือ **251 รีวิวสะอาด**
ตัวเลขทุกตัวในรายงานใช้ชุด 251 นี้ ไม่ใช่ 300

### 2.4 คู่มือติดป้ายขัดกันเอง — ทำให้บางหมวดแย่โดยไม่เกี่ยวกับข้อมูลน้อย

เจอสองครั้ง และทั้งสองครั้ง "เติมข้อมูลเพิ่มก็ไม่หาย"

**หมวด 2 (ความคิดเห็นทั่วไป)** คู่มือบรรทัดหนึ่งบอก "ไหว้พระ → หมวด 10"
อีกสองข้อบอกให้ใช้หมวด 2 ชุดเทรนกับชุดประเมินจึงลากเส้นแบ่งคนละที่

**หมวด 10 (สถานที่ท่องเที่ยว กิจกรรม สินค้า)** วัดได้ recall 0.923 แต่ precision
เพียง 0.414 ทายเกิน 17 ครั้ง และ gold บอกว่า 11 ครั้งในนั้นเป็นหมวด 3
ตรวจแล้วไม่ใช่ปัญหาข้อมูลน้อย — silver มีหมวด 10 ถึง 191 ตัวอย่าง (gold มี 13)

**แก้แล้วทั้งสองครั้ง** โดยให้ผู้ใช้ตัดสินกติกา แล้วตรวจชุด silver ด้วยตาทีละใบ
(ไม่ใช้ regex เหมารวม เพราะคำว่า "วัด" "น้ำตก" "ตลาด" อยู่ได้ทั้งบริบทกิจกรรม
และบริบทสภาพสถานที่ — การเหมารวมจะเสียตัวอย่างที่ถูกต้องไป)

**บทเรียนที่ต้องเขียนในเล่ม** เมื่อหมวดใดคะแนนต่ำ ต้องแยกให้ออกก่อนว่าเป็น
"ข้อมูลน้อย" หรือ "คู่มือขัดกันเอง" สองอย่างนี้แก้ด้วยวิธีตรงข้ามกัน
ถ้าเป็นอย่างหลังแล้วไปเติมข้อมูล จะยิ่งเพิ่มตัวอย่างที่ขัดกันเข้าไปอีก

### 2.5 การแปลงหมวด v1 → v2 มีจุดที่กำกวม

ชุดหมวดเดิมมี 12 หมวด ชุดใหม่มี 11 หมวด การยุบมีสองคู่ที่ตรงไปตรงมา
("การเดินทางและที่จอดรถ" + "ข้อมูลและป้ายบอกทาง" → 7 ·
"สิ่งอำนวยความสะดวก" + "ความปลอดภัย" → 9)

แต่หมวด **"อื่นๆ" ของ v1 แยกได้สองทาง** — ไปหมวด 10 (สถานที่/กิจกรรม/สินค้า)
หรือหมวด 11 (อื่นๆ/นอกเรื่อง) ก็ได้ ผู้ใช้สั่งให้ตั้งเป็น 10 ไว้ก่อนแล้ว
mark `needs_review` ปัจจุบันมี **38 แถว** ที่ยังรอคนตรวจ

### 2.6 ความรุนแรง (severity) ไม่ได้ย้ายมาชุดใหม่

`review_aspects.severity` **ว่างทั้ง 129,918 แถว** ความรุนแรงจึงมีแต่ในป้ายชั้นเดิม

| ค่า | จำนวน (analyzed_reviews) |
|---|---|
| low | 109,931 |
| high | 2,393 |
| medium | 1,318 |
| (null) | 449 |

**ผลต่อระบบ** endpoint ที่ขับด้วย severity ย้ายมาชั้นใหม่ไม่ได้
`/top-places` จึงยังอ่านป้ายชั้นเดิมทั้ง endpoint และ `/zones`, `/summary`,
`/zones/{zone}/pain-points` ต้องมี**ตัวนับคำบ่นสองตัว** (`neg` ชุดใหม่ สำหรับ
`complaint_rate` และ `neg_legacy` ชั้นเดิม สำหรับ `severity_share`)
ไม่งั้นตัวเศษกับตัวส่วนจะมาจากคนละชั้น

**ผลต่อการอ่านตัวเลข** `high + medium + low` **ไม่เท่ากับ** `negative_count`
และไม่ควรเท่า (ของเดิมก็ไม่เท่าอยู่แล้ว เพราะ 449 แถวเป็นคำบ่นแต่ severity เป็น NULL)

### 2.7 ความรุนแรงไม่เคยถูกตรวจว่าสะท้อนอะไร

`low` คิดเป็น 96.3% ของแถวที่มีค่า ซึ่งแปลว่าตัวชี้วัดนี้แยกแยะได้น้อย
และไม่มีการวัดเลยว่า "รุนแรงสูง" ตรงกับความเห็นของคนหรือไม่
**ตัวเลข severity ทุกตัวในงานนี้จึงยังไม่มีหลักฐานรองรับ**

### 2.8 ชุดตรวจของคน 96 แถวถูกกรอกตอนที่ยังไม่มีหมวด 14 ตัวเลขหลังย้ายอ้างไม่ได้

เมื่อ 2026-10-13 ผู้ใช้ตรวจป้าย 96 แถวแบบปิดตา (ไม่เห็นป้ายของ Claude) ได้

| ตัววัด | ค่า |
|---|---|
| อารมณ์รวม ตรงกัน 90.6% · kappa | **0.7790** |
| อารมณ์รายหมวด ตรงกัน 91.9% · kappa | **0.8117** |
| หมวด micro-F1 (precision 0.740 · recall 0.871) | **0.8000** |
| negative ตรงกัน 5/5 · คนใส่เกิน 1 | recall 1.000 · precision 0.833 |

**ข้อค้นพบที่สำคัญกว่าตัวเลข** ธง `no_specific_topic` ถูกใช้ **0 จาก 6 ครั้ง**
ผู้ติดป้ายเลือกเดาหมวดทุกครั้ง และการเดาสร้างป้ายที่ข้อความไม่รองรับ
(เช่น `47509` ซึ่งเป็นรีวิวแปลด้วยเครื่อง ได้ `2+` ทั้งที่ไม่มีคำใด
เกี่ยวกับบรรยากาศ) จึงเปลี่ยนธงเป็นหมวด 14 ความประทับใจโดยรวมในชุด v3.2

**ผลข้างเคียงที่ทำให้ตัวเลขใช้ไม่ได้** หลังย้าย 9 แถวที่ติดธงไปเป็นหมวด 14
คะแนนเปลี่ยนเป็น recall 0.841 · micro-F1 **0.7872** (คนไม่ใส่ 22 เป็น 28)
เพราะ 6 แถวที่เคยติดธงมี `14+` หรือ `14n` ใน gold แล้วแต่ผู้ตรวจใส่หมวดอื่น

**0.7872 ไม่ใช่การวัดความสอดคล้องระหว่างคน** แต่เป็นการนับว่าผู้ตรวจ
ไม่ได้ใช้ตัวเลือกที่คู่มือตอนนั้นยังไม่มี ตัวเลขที่อ้างได้คือ

> micro-F1 **0.8000** · kappa **0.7790** เทียบกับ gold รุ่นที่ผู้ตรวจเห็นตอนกรอก
> ซึ่งเป็นรุ่นที่ผู้ตรวจเห็นตอนกรอก หลังจากนั้น gold เปลี่ยนเป็น v3.2
> ที่เพิ่มหมวด 14 **จึงยังไม่มีตัวเลขความสอดคล้องของ v3.2**

**และแก้ด้วยการให้กรอก 6 แถวนั้นใหม่ไม่ได้** เพราะผู้ตรวจเห็นคำตอบไปแล้ว
จากการสนทนาที่นำไปสู่การสร้างหมวด 14 การกรอกใหม่จะไม่ใช่การตรวจแบบปิดตา
ต้องสุ่มชุดใหม่จากแถวที่ผู้ตรวจยังไม่เคยเห็น พร้อมคู่มือ v3.2 **ยังไม่ได้ทำ**

**ร่องรอยการแก้ป้าย** การย้าย 9 แถวทำด้วย `scripts/migrate_gold_v3_2_cat14.py`
ไฟล์เดิมสำรองที่ `backup/gold_before_cat14_20261013_074639/`
แถวที่ถูกย้ายมี `label_source = migrated_v3_2_cat14` และสภาพเดิมอยู่ในคอลัมน์ `note`

### 2.9 หมวดที่ตัวอย่างไม่ถึง 20 เติมด้วยการสุ่มเจาะจงซึ่งมีอคติ

ชุด gold v3.2 มี 199 แถว แต่ 6 หมวดมีตัวอย่างไม่ถึง 20 จึงวัด P/R รายหมวดไม่ได้

ข้อความที่แต่งขึ้นจะไม่มีคำพิมพ์ผิด ไม่มี metadata ปน ไม่มีรีวิวที่แปลด้วยเครื่อง

**การสุ่มล้วนทำไม่ได้ในทางปฏิบัติ** คิดจากอัตราในชุด gold ปัจจุบัน

หลังแปลงชุด gold v2 (154 แถวแปลงเครื่อง + 142 แถวที่ผู้ใช้อ่านเอง ดู 2.10)
ชุด gold โตเป็น **495 แถว** และหมวดที่เคยขาดผ่านเกณฑ์ไปเองเกือบหมด

**ความต้องการของการสุ่มเจาะจงจึงลดจาก 58 แถว เหลือ 8 แถว และเหลือหมวดเดียว**

**บทเรียน** ต้องใช้ข้อมูลที่มีอยู่แล้วให้หมดก่อน จึงค่อยยอมรับวิธีที่มีอคติ
ลำดับที่ถูกคือ แปลง v2 -> อ่านแถวที่กำกวม -> วัดว่าหมวดไหนยังขาด -> สุ่มเจาะจง
เฉพาะเท่าที่จำเป็น การทำสลับลำดับทำให้เกือบเอาตัวอย่างที่มีอคติ 58 แถว
เข้าชุดวัดผลทั้งที่ไม่จำเป็นเลย 50 แถว

**อคติที่ต้องประกาศ เฉพาะหมวด 14**
กอง A (6 จาก 8 แถว) เป็นเคสที่โมเดล v2 หาเจออยู่แล้ว recall ที่วัดได้จึงสูงกว่า
ความจริง และสืบทอดจุดบอดของ v2 มาด้วย กอง B (2 แถว) มีไว้ถ่วง แต่ถ่วงได้ไม่หมด
ที่มาของแต่ละแถวอยู่ใน `reports/evaluation/gold_v3_2_rare_manifest.csv`
**หมวด 1-13 ไม่มีอคตินี้เลย** เพราะไม่ได้ใช้การสุ่มเจาะจง

**ถ้าหลังกรอก 8 แถวแล้วหมวด 14 ยังไม่ถึง 20** ให้รายงานเป็น "ข้อมูลน้อย"
เหมือนหมวด 13 ไม่ต้องไล่สุ่มเพิ่มจนชุดเอียง — การบอกว่าวัดไม่ได้
ซื่อสัตย์กว่าการได้ตัวเลขจากตัวอย่างที่คัดมาจนไม่เป็นตัวแทน

**สองหมวดที่ตัดสินใจว่าวัดไม่ได้ ไม่เติมตัวอย่าง** (ตกลงเมื่อ 2026-10-13)

- **หมวด 13 อื่นๆ** เป็นหมวดเศษเหลือ 0.92% ของฐาน ตัวเลขรายหมวดของ
  หมวดเศษเหลือไม่มีความหมาย และการสุ่มเจาะจงจะยิ่งทำให้เอียง
- **ป้าย `14-` ติโดยรวมแบบไม่ระบุประเด็น** มีเพียง 43 ใบในขอบเขตที่ความยาว
  ไม่เกิน 22 อักขระ การค้นให้ได้ 20 ตัวอย่างต้องเจาะจงหนักจนวัดอะไรไม่ได้

### 3.5 ยังไม่ได้วัดความผันผวนของการแบ่งข้อมูล

ส่วนแบ่ง train/val ตรึงไว้คงที่ตลอด (ด้วย `SEED` ที่ห้ามเปลี่ยน) sd ที่วัดได้จึงเป็น
**ความผันผวนของการเทรน** เท่านั้น ยังไม่รวมความผันผวนที่เกิดจากการแบ่งข้อมูลคนละแบบ
ซึ่งต้องทำ cross-validation

### 3.6 3 seed ต่อ config ยังน้อย

sd ที่ได้เป็นค่าประมาณคร่าว ๆ และ **sd ของ sd เองก็ใหญ่** ถ้ามีเวลาควรเพิ่มเป็น 5–10 seed
เกณฑ์ "ผลต่างเกิน sd" ที่ใช้เลือก config **ไม่ใช่การทดสอบนัยสำคัญทางสถิติ**
ด้วย n=3 ต่อชุด t-test ก็ยังไม่มีกำลังพอ เกณฑ์นี้ใช้กันตัวเองเผลอสรุปเท่านั้น

### 3.7 ห้ามใช้ accuracy เป็นตัวชี้วัดหลัก

ข้อมูลเอียงมาก (88% เป็นบวก) ทายว่า "บวก" ทุกรีวิวได้ accuracy สูงมากแล้ว
ขณะที่ macro-F1 ของการทายแบบนั้นได้แค่ 0.3130

**กติกาที่ใช้ในงานนี้** รายงาน macro-F1 + per-class P/R ของ negative +
confusion matrix + baseline ทายบวกหมด ทุกครั้ง

### 3.8 baseline 3 ใน 4 ตัวก็แกว่ง

| baseline | mean ± sd |

วัดหลังแก้ขอบเขต (2026-10-13) เทียบแต่ละชั้นกับ baseline ของตัวเอง

| ชั้น | ระบบ | baseline | ผลต่าง | คิดเป็น |
|---|---|---|---|---|
| หมวด micro-F1 | 0.8816 ± 0.0080 | 0.6279 ± 0.0144 | +0.2537 | **17.7 sd** |
| อารมณ์รวม macro-F1 | 0.7118 ± 0.0268 | 0.3130 ± 0.0000 | +0.3987 | **14.9 sd** |
| อารมณ์รายหมวด macro-F1 | 0.7035 ± 0.0359 | 0.5800 ± 0.0047 | +0.1235 | **3.4 sd** |
| **ทั้งระบบ micro-F1** | **0.8258 ± 0.0183** | **0.8130 ± 0.0088** | **+0.0127** | **0.70 sd** |

baseline ของแต่ละชั้นคือ: หมวด = เดาหมวดเดียวที่คะแนนสูงสุด · อารมณ์รวม =
ทายบวกหมด · อารมณ์รายหมวด = ใช้อารมณ์รวมกับทุกหมวด · ทั้งระบบ = ใช้อารมณ์รวมแทน

**สิ่งที่ต้องเขียนในเล่มตรง ๆ** สามชั้นแรกชนะ baseline ขาดลอย แต่**เมื่อต่อกัน
เป็นระบบ ผลต่างเหลือ 0.70 sd ซึ่งตามกฎของงานนี้ถือว่าเท่ากับ baseline**
แปลว่าความซับซ้อนของการแยกอารมณ์รายหมวดยังไม่ให้ประโยชน์ที่วัดได้
เมื่อเทียบกับการเอาอารมณ์รวมไปแปะทุกหมวดที่ตรวจเจอ

**เหตุผลที่มองเห็นได้** อารมณ์รายหมวดคลาส `neutral` ได้ F1 เพียง 0.3038 ± 0.0732
(ดู 4.2) ซึ่งเป็นคลาสที่ทำให้ระบบต่างจาก baseline มากที่สุด เมื่อคลาสนั้นพลาด
ประโยชน์ของการแยกรายหมวดจึงถูกกลบ

**ข้อนี้เปลี่ยนจากเอกสารรุ่นก่อน** รุ่นก่อนระบุว่า "ชนะแค่ 2 sd" โดยวัดบน
ชุดข้อมูลที่มีสถานที่นอกขอบเขตปนอยู่ (ชุดเทรน 49/996 · ชุดประเมิน 7/251)
หลังตัดออกและเทรนใหม่ด้วย config เดิม ผลต่างลดจาก 2.03 sd เหลือ 0.70 sd
**ห้ามอ้างตัวเลขรุ่นก่อน** ดู 2.11 สำหรับรายละเอียดการแก้

**การปรับปรุงต้องเริ่มจากการเพิ่มชุดประเมิน ไม่ใช่เพิ่มชุดเทรน**
เพราะตอนนี้วัดไม่ได้ว่าแก้แล้วดีขึ้นจริงหรือเป็นความผันผวน
(เคยพยายามแก้หมวด 10 ด้วยการตรวจชุดเทรนทีละใบ 191 รายการ แล้วผลออกมาผสม
จนสรุปไม่ได้ว่าดีขึ้นหรือแย่ลง — ดูหัวข้อ 2.4 และ 3.3)

### 4.2 อารมณ์ `neutral` ทำได้แย่ที่สุด

F1 ของ `neutral` ในอารมณ์รายหมวดอยู่ที่ 0.3038 ± 0.0732 ต่ำกว่า `positive`
และ `negative` มาก เพราะ `neutral` เป็นคลาสที่นิยามคลุมเครือที่สุดและมีตัวอย่างน้อย

### 4.3 ระบบวัด "การแสดงความไม่พอใจ" ไม่ใช่ "การมีอยู่ของปัญหา"

ข้อเสนอแนะที่พูดอย่างสุภาพโดยไม่ติจะถูกจัดเป็น `neutral`
และปัญหาที่ไม่มีใครเขียนถึงจะไม่ปรากฏเลย
**ตัวเลขทุกตัวจึงเป็นตัวแทนของ "เสียงที่ดังพอจะถูกเขียนลงรีวิว" ไม่ใช่ของปัญหาจริง**

### 4.4 การตัดประโยคย่อยช่วยน้อยกว่าที่คาด

เคยคาดว่าการตัดประโยคที่มีคำขัดแย้ง ("แต่", "ถึงแม้") จะช่วยได้มาก วัดจริงแล้ว
ที่ระดับข้อมูลทั้งหมดมีเพียง **1.12 ประโยค/รีวิว** และช่วยแค่ **+0.016 F1**
เพราะคำขัดแย้งโผล่ในรีวิวแค่ประมาณ 15%

### 4.5 ไม่ได้จูนอะไรนอกจาก epoch

เลือก config โดยวัดเฉพาะ `epochs` ยังไม่ได้ลอง `lr`, `batch_size`, `max_length`,
`pos_weight` หรือกลยุทธ์การเลือก threshold ซึ่งอาจให้ผลมากกว่า epoch

### 4.6 โมเดลตัวอื่นในโฟลเดอร์ `models/` ย้อนทำซ้ำไม่ได้

`wangchanberta-sentiment` และ `wangchanberta-category` (รุ่นเดิม single-label)
เทรนก่อนที่จะเพิ่มการบันทึก config จึงไม่มี `run_seed`/`epochs`
**ตัวเลขจากสองตัวนี้ใช้อ้างอิงในเล่มไม่ได้** ใช้ได้แค่เป็น baseline เชิงเปรียบเทียบ
และเป็นจุดตั้งต้นของการเทรนต่อ (`START_FROM`)

แต่**นี่คือการแก้ด้วยการอธิบาย ไม่ใช่การแก้ที่ต้นเหตุ**

### 5.2 สแนปช็อตเก่าเป็นหมวดชุด v1 และไม่ถูกแก้ย้อนหลัง

สแนปช็อต 468 แถวที่เก็บไว้ก่อนการย้ายเป็นชุด v1 ทั้งหมด
สแนปช็อตที่เก็บต่อจากนี้จะเป็น v2 (`take_snapshot.py` ตั้ง `category_version='v2'`)

**ผลต่อ `/snapshot-compare`** การเทียบสแนปช็อต v1 กับ v2 ตรง ๆ **ทำไม่ได้**
เพราะชุดหมวดต่างกัน ตอนนี้ยังไม่มีการเตือนผู้ใช้ที่ชั้น API เมื่อเทียบข้ามรุ่น —
**ข้อนี้ยังไม่แก้** ตัวกรองหมวด "ไม่ใช่ปัญหา" แก้แล้วให้ครอบคลุมชื่อทั้งสองรุ่น
(v1 ใช้ "ไม่ระบุปัญหา" v2 ใช้ "ไม่ระบุประเด็น" ต่างกันคำเดียวตรงท้าย)

### 5.3 ค่าตั้งต้นของ `status` ไม่เหมือนกันทุก endpoint

บาง endpoint ตั้งต้น `operational` บาง endpoint ตั้งต้น `all` โดยเจตนา
เพื่อไม่ให้ผู้เรียกเดิมได้ผลเปลี่ยน **ผลคือถ้าไม่ส่ง `status` มาเหมือนกัน
ตัวเลขจากสอง endpoint จะมาจากประชากรคนละชุด** และเทียบกันไม่ได้

### 5.4 `/heatmap` ใช้ฐานคนละชุดกับ `/summary`

`high_count` ใน `/heatmap` **ไม่กรอง sentiment และไม่กรอง `text_clean`**
จึงไม่ใช่ตัวเลขเดียวกับ `/summary` หรือ `/top-places`
ยังคงไว้แบบนี้เพื่อไม่ให้ผู้เรียกเดิมได้ผลเปลี่ยน แต่**ห้ามเอาไปวางข้างกันบนหน้าจอ**

### 5.5 รีวิว 3 รายการมีข้อความแต่ไม่มีแถวใน `review_aspects`

ไม่กระทบตัวเลขในทางปฏิบัติ (3 จาก 73,013) แต่แสดงว่าการ reanalyze ไม่ครบ 100%

ทั้งที่ผู้รีวิวไม่ได้พูดถึงราคา) และผู้ใช้ที่ติดป้ายเองเจอ 3 ใบในชุดตรวจ
**ไม่ใส่หมวดราคาเลยทั้ง 3 ใบ = ผู้ใช้ถูก gold ผิด**

**ทำไมแก้ที่ต้นทางไม่ได้** `text_hash = md5(clean_review_text(text))`
ถ้าแก้ `clean_review_text()` ให้ลอก metadata **hash ของทุกแถวจะเปลี่ยน**
ตัวกันซ้ำที่ผูกกับ hash จะพัง และ scraper รอบถัดไปจะ insert ซ้ำทั้งตาราง
เคยเกิดจริงแล้ว 3,453 แถว (บันทึกไว้ใน git history) จึงตั้งกฎว่า
**ห้ามแก้ `clean_review_text()`** ไม่ว่าด้วยเหตุผลใด

**ทางแก้ที่ทำได้ โดยไม่แตะ `text_hash`**

1. ลอก metadata ตอนวิเคราะห์และตอนแสดงผล (ไม่แตะคอลัมน์ที่เก็บไว้)
2. เพิ่มคอลัมน์ `text_for_nlp` เก็บข้อความที่ลอกแล้ว ใช้เป็น input ของโมเดล
3. ตัด 165 รีวิวที่ไม่เหลือคำรีวิวออกจากตัวส่วนของทุกสัดส่วน
4. กติกาติดป้าย v3 `google_metadata_is_not_review_text` สั่งให้คนติดป้ายอ่านข้าม
   ส่วนนี้แล้ว (บันทึกใน `shared/categories_v3.json`)

### 6.2 ป้ายชุดเทรนชุดแรกถูกเขียนทับจนเหลือสำเนาเดียว

ไม่สามารถย้อนดูได้ว่าป้ายรอบแรกต่างจากรอบปัจจุบันอย่างไร
จึงไม่สามารถวัดได้ว่าการแก้คู่มือแต่ละครั้งเปลี่ยนป้ายไปกี่แถว

**แก้ที่กระบวนการแล้ว** ทุกการแก้ชุด silver ตั้งแต่นั้นมาสำรองไว้ก่อนเสมอ
(`backup/silver_before_cat2_*`, `backup/silver_before_cat310_*`)

### 6.3 ความครบถ้วนของการค้นหาสถานที่วัดไม่ได้

ไม่ทราบว่า 762 สถานที่เป็นกี่เปอร์เซ็นต์ของสถานที่ที่ควรอยู่ในขอบเขต
**และขอบเขตโซนถูกตรึงไว้** ห้ามแก้หรือรัน `assign_zones` ใหม่จนกว่าจะวัด
ความครบถ้วนของการ discover ได้

## 7. สิ่งที่ยังไม่รู้ — วัดไม่ได้ด้วยข้อมูลที่มี

1. **เพดานความแม่นที่เป็นไปได้** ต้องให้คนตรวจป้ายแล้วคำนวณ Cohen's kappa
2. **ความครบถ้วนของการเก็บรีวิว** Google ไม่บอกจำนวนรีวิวทั้งหมดที่เชื่อถือได้
3. **ว่าสัดส่วนดาวที่เห็นสะท้อนความจริงหรือเป็นผลของวิธีเก็บ**
4. **ความผันผวนจากการแบ่งข้อมูล** ต้องทำ cross-validation
5. **ว่าผู้ใช้จริงเห็นด้วยกับหมวดและอารมณ์ที่ระบบจัดให้หรือไม่**
   ไม่มีการทดสอบกับผู้ใช้เลย
6. **ว่า severity สะท้อนความรุนแรงที่คนรู้สึกจริงหรือไม่** (ดูข้อ 2.7)
7. **ว่าผลลัพธ์ย้ายไปใช้กับจังหวัดอื่นได้หรือไม่** เทรนและประเมินบนพิษณุโลกเท่านั้น
